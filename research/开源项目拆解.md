# 开源电商 Skill 源码拆解

调查日期：2026-09-15。  
范围：5 个公开仓库的目录、关键技能入口、能力说明、部分执行器和许可证。保存并校验了 44 个选取的参考文件，文件内容均与所取得的仓库目录对象一致。未运行第三方生成脚本、未调用其付费服务，以下不构成出图质量或实际价格的横向测试。

固定版本与逐文件链接保存在 [来源快照](来源快照.json)。本文件说明参考项目实际如何工作；本项目的最终取舍见 [项目思路](../项目思路.md)。

## 1. 总体判断

这些项目开放的主要内容是任务指导、提示组织、调用脚本和部分本地处理逻辑。真正制作位图时，需要相应的模型或媒体执行路径。

不能笼统说它们全部强制使用作者自家平台。美图两套项目依赖其服务；dLazy 支持多种模型供应商；ecommerce-image-suite 也提供多供应商配置；OpenDesign 使用它自己的媒体执行层，并有供应商配置。用户可能绕开某个作者平台，但仍需要另行处理模型或执行环境依赖。

本项目的差异应定义为：在具备图片工具的 Codex 环境里，直接使用会话能力，使用者无需配置额外生成平台账号或 API Key。这个目标与 MIT、Apache 等代码许可证问题分开表述。

## 3. DesignKit：最完整的简易套图交付路径

来源：[电商套图技能](https://github.com/meitu/designkit-skills/blob/1b3bea5215903f802d839c54e3fc90706f15c7c7/skills/designkit-ecommerce-product-kit/SKILL.md)、[执行程序](https://github.com/meitu/designkit-skills/blob/1b3bea5215903f802d839c54e3fc90706f15c7c7/scripts/ecommerce_product_kit.py)。

### 已有功能

- 抠图、去背景、透明或白底处理。
- 图片变清晰。
- 根据商品图形成卖点建议。
- 收集平台、国家、语言、比例等配置。
- 按需获取风格候选，再提交套图制作。
- 轮询进度，自动下载，按商品、序号和图位命名。
- 用户看图后可以换风格重做。

### 核心思路

面向卖家提供从输入到成品的对话。技能不是只交给用户一段提示词，而是负责收集必要信息、启动制作并把实际文件拿回来。

源码中可以看到具体的远端服务地址、凭证检查、上传、风格任务、出图任务和轮询逻辑。风格候选与部分决策由服务端提供。因此它不能仅删除 API Key 检查就变成 Codex 原生版本。

### 吸收与调整

吸收完整交付链路和文件归档。将卖点理解、风格方案、逐图计划搬到 Codex；图像制作替换为会话内置工具。

原技能对信息收集轮次有较强固定要求，还设置特定平台、市场和语言默认值。本项目改为按当前输入与实际缺项推进，不要求用户重复确认已提供的信息，也不固定把未知商家当成美国亚马逊卖家。

## 4. Meitu Skills：多图角色、空间融合和修改记录

来源：[仓库](https://github.com/meitu/meitu-skills/tree/95e563c0a695094403ccf77eb8fe7bd8bb58939c)、[商品替换](https://github.com/meitu/meitu-skills/blob/95e563c0a695094403ccf77eb8fe7bd8bb58939c/skills/meitu-product-swap/SKILL.md)、[多角度展示](https://github.com/meitu/meitu-skills/blob/95e563c0a695094403ccf77eb8fe7bd8bb58939c/skills/meitu-product-view/SKILL.md)、[图片适配](https://github.com/meitu/meitu-skills/blob/95e563c0a695094403ccf77eb8fe7bd8bb58939c/skills/meitu-image-adapt/SKILL.md)。

### 与电商最相关的功能

| 类别 | 包含的任务 |
| --- | --- |
| 商品与场景 | 商品替换进场景、一个商品对应多个场景、多个商品分别套用场景 |
| 展示方式 | 商品多角度、特写、背景模式 |
| 图片处理 | 抠图、修复、清晰化、文字替换、背景替换 |
| 版面与投放素材 | 海报、轮播图、扩图和不同尺寸适配 |
| 人物与服饰 | 换装、试穿、人物编辑 |
| 扩展媒体 | 图生视频、视频编辑、动作迁移等 |
| 项目复用 | 场景偏好、项目规则、反馈与版本记录 |

本次重点阅读电商相关的场景技能，不把整个仓库全部原子功能都视为已审核。

### 可借鉴的方法

商品替换技能把场景参考与真实商品明确区分，并约定多图位置；制作方案包含位置、透视、保留区域和光线。对用户修改意见，也会区分商品身份、位置角度、场景风格等问题。

部分技能区分项目模式和一次性任务，允许长期偏好与当前修改分开处理。对持续经营店铺，这种区分有价值：这次做一张节日图不应自动改变今后全部商品的风格。

### 调整

这些任务的执行普遍要求 meitu CLI 和服务凭证。本项目保留分析与修改方法，由 Codex 直接处理。

多角度方法中，生成正面后再派生其他角度可以帮助画面一致，但会增加把生成细节当作真相的风险。本项目优先使用每个角度的真实参考；看不见的结构保持未知。

扩图、分辨率和修复参数属于对方工具合同，不能照搬成内置 image_gen 的参数保证。参考项目中的个人视觉记忆也不会整体引入电商技能，只保留店铺和商品真正需要的资料。

## 5. dLazy Ecommerce Skills：覆盖面和工程化最值得参考

来源：[功能索引](https://github.com/dlazy-ai/ecommerce-skills/blob/5873d47743ccf45f468d893e1930c03d1dc960dd/README.md)、[供应商执行层](https://github.com/dlazy-ai/ecommerce-skills/blob/5873d47743ccf45f468d893e1930c03d1dc960dd/shared/scripts/lib/providers.mjs)、[批量执行](https://github.com/dlazy-ai/ecommerce-skills/blob/5873d47743ccf45f468d893e1930c03d1dc960dd/shared/scripts/batch.mjs)。

### 26 项功能归并

| 任务组 | 参考项目中的能力 |
| --- | --- |
| 商品上身与搭配 | 平铺服装上身、鞋包饰品穿戴、多单品搭配融合 |
| 单图扩展 | 换模特与背景、完整套图、详情页模块 |
| 创意图 | 按场景与构图描述生成新视觉 |
| 商品编辑 | 立体展示、服装提取、面料替换、细节放大、种草穿搭、卖点主图、换背景、去水印文字、材质增强、商品精修 |
| 批量与质量 | CSV 批量、AI 视觉检查、平台规格检查、品牌规范 |
| 上架与复盘 | A/B 主图与复盘、多语言和区域本地化 |
| 视频 | 主图视频、商品广告视频、UGC 口播类视频 |

### 应吸收的五件事

1. **公共品牌要求与每个商品的变化项分开。** 品牌文件保存背景、光线、构图和文字风格，SKU 只提供自己的特征。
2. **先做代表样本，再批量。** 避免错误方案扩散到整个目录。
3. **任务状态落盘。** 记录成功与失败，支持中断后继续。
4. **生成与检查相连。** 把发现的问题写成下一次明确的修改要求，并有轮次限制。
5. **技术检查与视觉检查分开。** 文件信息可以测量，商品真实性需要视觉和事实对照。

### 源码揭示的限制

以下是固定版本中的代码观察，不是对其所有未来版本或实际出图质量的评价。

**自动视觉检查只传入当前生成文件。** 在 run_loop 中，检查调用的图片参数是 files[0]，没有同时附带原始商品图。它可以观察画面异常，却缺少直接判断“与卖家原商品是否一致”的完整依据。同一路径也只检查首个生成文件。  
来源：[run_loop.mjs](https://github.com/dlazy-ai/ecommerce-skills/blob/5873d47743ccf45f468d893e1930c03d1dc960dd/shared/scripts/run_loop.mjs)。

**未知的规格结果没有被明确挡住。** 该循环把不等于 reject-risk 的规格结论视为可接受条件，因此 unknown 也可能进入接受路径。风险等级与建议人工修改的文本也没有完全形成独立状态约束。  
本项目采用明确的未检查、无法判断和需修改状态，不能仅看一个整体风险词就推进。

**主体占比是近似测量。** check_listing.py 从边缘估计背景，再用色差形成包围盒，计算包围盒面积相对整图的比例。这不是精确分割，也不代表所有平台对主体占比的口径。白色／透明商品、接近背景的材质和阴影需要额外判断。  
来源：[check_listing.py](https://github.com/dlazy-ai/ecommerce-skills/blob/5873d47743ccf45f468d893e1930c03d1dc960dd/shared/scripts/check_listing.py)。

**恢复任务主要按 SKU 完成记录过滤。** 已完成 SKU 被跳过的方式很直接，但本项目还应核对原图、品牌和文件是否变化，避免用户换图后旧结果继续被当作完成。

**相同提示词不保证画面绝对一致。** 固定品牌段落是一种约束方法，不能把文档中关于一致性的强表述当作统计验证。

**多供应商不等于零 API。** provider 源码确实有不同供应商的调用路径；选择 OpenAI 仍是带 API Key 的接口调用，与本项目直接用 Codex 会话内置工具不同。品牌规则和部分本地检查可以独立使用，但真正出图仍依赖执行后端。

## 6. OpenDesign：任务边界和交付结构清楚

来源：[Ecommerce Image Workflow](https://github.com/nexu-io/open-design/blob/d465086b2c9264c47c5d3e1cfeb8cfb2864a41d4/skills/ecommerce-image-workflow/SKILL.md)、[媒体配置](https://github.com/nexu-io/open-design/blob/d465086b2c9264c47c5d3e1cfeb8cfb2864a41d4/apps/daemon/src/media/config.ts)。

### 功能与流程

该技能要求真实商品参考图，默认组织基础展示、单一卖点和场景三张图。先记录商品形状、颜色、标签、结构与比例等不能改变的特征，再为各个图位生成制作要求。

交付包含图片清单和小型 HTML 预览。未提供参考图时，不直接生成一个想象商品冒充真实产品；文案也限制虚构认证和性能数字。

### 吸收与调整

这是一个适合第一版借鉴的清晰任务范围。图片清单记录输入、输出、图位和注意事项，有利于改图、追踪与审核。

它明确通过 OpenDesign 的 media generate／wait 工作流执行。相关媒体配置包含供应商配置与凭证处理。因此其工作流文件不能作为无需 OpenDesign 的 Codex 原生执行方案直接使用。

本项目独立实现商品资料、图位计划与预览；不引入该运行环境和媒体适配层，也不沿用任何读取外部认证存储的路径。

## 7. Ecommerce Image Suite：动态内容策划与图文衔接

来源：[技能入口](https://github.com/wzj177/ecommerce-image-suite/blob/2d508bd990df0397026406f210a5915b2c955469/SKILL.md)、[动态提示架构](https://github.com/wzj177/ecommerce-image-suite/blob/2d508bd990df0397026406f210a5915b2c955469/references/dynamic-prompt-architecture.md)、[供应商说明](https://github.com/wzj177/ecommerce-image-suite/blob/2d508bd990df0397026406f210a5915b2c955469/references/providers.md)。

### 功能

- 支持单张和多张商品参考，区分平铺、挂拍和模特实拍。
- 提取可见特征，生成结构化商品描述与卖点。
- 选择平台与白底、卖点、材质、场景、模特、拼图等图位。
- 根据商品与卖点组织每张图的内容。
- 生成平台文案与详情页 HTML。
- 可选视频制作与人物参考。
- 按商品任务分目录，保存结果清单。

### 吸收与调整

最大的优点是把商品理解用于图片设计，而不只是把一个商品名填进固定模板。它也明确把 Agent 自身视觉作为优先路径，文案和 HTML 可直接由 Agent 完成。

但它同时把图片供应商 Key 检测放在整项任务最前面，缺 Key 时要求连商品分析都停止。对于 Codex 已有图片工具的环境，这种前置条件不适合。

不同说明中还存在模型、图类型数量和参考图使用方式的不同表述，本项目不会把文档中的示例参数当作已统一验证的接口事实。支持多图分析时，必须确保实际图片制作也获得必要参考，不能只把多图压缩成文字描述就声称保真。

其风格方案和尺寸规范属于参考项目的设计选择或待核验资料，不直接作为“淘宝就应这样、拼多多就应那样”的固定审美规则。

## 8. 合成后的工作流

把上述优点归并后，可以形成以下顺序：

```text
确认任务与原生工具
  → 查看商品原图，区分图片角色
  → 整理真实特征、卖点来源、缺失信息
  → 读取当前店铺已有规范
  → 安排各张图的目的和内容
  → Codex 调用内置图片工具
  → 原图与结果对照＋基础技术检查
  → 针对具体问题有限修改
  → 整理图片、文案、预览、清单与续做状态
```

重点不是把原有几十个技能文件放在同一个目录里，而是让相同的商品事实、品牌规则与结果状态被各个任务共享。否则功能越多，商品描述、默认设置、输出路径和审核标准越容易相互冲突。

## 9. 本项目采用与暂缓

| 决策 | 内容 |
| --- | --- |
| 直接吸收方法 | 图片角色、商品特征记录、图位计划、品牌规范、动态文案、交付清单 |
| 重写执行 | 内置图片工具调用、文件保存衔接、任务恢复、视觉对照、有限重做 |
| 保留但需实测 | 透明底、复杂标签、跨语言改图、精确规格、试穿、材质与细节 |
| 不沿用 | 厂商账号、充值提示、API Key 首步检查、第三方生成执行器、自动改用付费后端 |
| 不当作事实能力 | 单图还原不可见结构、真正 3D 重建、自动制造商品认证、生成后必然提高转化 |
| 暂缓 | 未确认有完整 Codex 原生路径的生成式视频与口播成片 |

## 10. 调查边界

本轮已经核对相关源码和依赖，足够支持架构取舍。还没有完成不同项目的实图效果测试，没有核验全部平台规则或最新模型价格，也没有将全部 44 个文件逐行作安全审计。

记录的 44 个文件是选取的调查快照，哈希校验说明文件版本可追溯，不代表这些项目的代码没有缺陷。下一步应以自己的原生能力小样和真实卖家商品验证为准。
